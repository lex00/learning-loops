Concept note · 2026-09-03

Language Universe

Looping, art-like scenes that each isolate one language capability and show it as a marble run. Meant to be stared at until the mechanism and its vocabulary fuse.

Why this exists

Most language-learning content holds the words steady and asks you to imagine the mechanism. This does the opposite. The mechanism stays on screen and cycles on its own, and the words are the only thing that changes when you toggle from Python to the language you are learning. You can read about a language elsewhere. This is for a different kind of learning: watching one thing loop until it is burned in.

The scene is a marble run

Marblea unit of work Track sectiona state that unit can be in Switcha point where language models differ Gatea capability this variant lacks Liftthe scheduler, returning marbles to the top Word on the trackthe vocabulary that fires at that moment

The loop is not a trick added on. Marbles drop, roll, finish, and the lift carries them back. That is what the machine does, so it can run forever.

Decisions settled so far

  • One scene per capability. No side-by-side code panes. The language is a skin on the scene.
  • Toggling morphs the scene on the same timeline and never resets it. Marbles already rolling keep rolling and take the new path at the next switch.
  • The cue is vocabulary fused to motion. When a marble gives up control, the word appears: await, park, block. Syntax is at most an optional hover whisper.
  • What you toggle is a variant, meaning a language plus an approach. Python has several entries. Morphing from Python threads to Python asyncio teaches something before leaving Python.
  • First set of variants: Python threads, Python asyncio, Go goroutines. Python is always the anchor you return to.
  • The participants in a scene are the variants that can do that thing. Absence teaches.
  • Partial capability is rendered, not hidden. A Python thread reaching parallel work hits the Global Interpreter Lock and stalls at a gate, in view of the marbles that pass.
  • All paths stay visible. The selected variant is lit, the others dim. Crowding is accepted as a rendering problem for later.
  • Loop rhythm leans toward a fixed skeleton with small timing jitter, which is also truer to concurrency. Not final.
  • Tooling is deliberately undecided. Marimo was considered and set aside because the scenes want rich motion and interaction. Choose tooling only after the first scene is designed on paper.

First topic: concurrency

Concurrency is a topic, not a concept. Each row below is a candidate scene, ranked by value for a novice: how early the mistake bites, and how differently the four participants behave on the track. Rows where all four do the same thing differently, like handing off a value, make good early scenes. Rows with a gap are where the roster shrinks and a gate appears. Rows two and three share a setup, a marble that does CPU work and never reaches the trapdoor, and can be one scene.

Row three was drawn first as the claw in Truly parallel, which is preemption: the scheduler taking a lane away. Yielding is the marble leaving its lane on purpose, with nothing to wait for, and the claw is the contrast it is toggled against. Row four, Handing off, is the first scene that needs both grammars: a box between the marbles, and a pocket for the marble the box stops.

What varies between models is a short list, and each item can be a visual dimension rather than a sentence: how many things truly run at once becomes lanes; who owns scheduling becomes whether a visible runtime or the OS moves marbles; what causes a wait becomes where a marble stops; how units talk becomes a hand-to-hand pass or a shared box with a lock; and the cost of a unit becomes its weight, so a thread reads heavy and a goroutine reads light.

Next step

Recommended

Design the base scene on paper first: a marble giving up control at a wait point. Every other scene is that track with something added, so the grammar settled here gets reused everywhere.

Alternative

Start from the stall scene, since it is the one worth staring at. It works, but it means designing the base track implicitly along the way.

Things to decide for the base scene: the states along the track, where the switch sits for each of the three variants, the word that appears at the wait point for each, and what the lift does differently under cooperative versus preemptive scheduling.

Planning only. Nothing has been built, and no tooling has been chosen.
